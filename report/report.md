## 一、实验目标与整体思路

Lab2 建立了高地址内核映射，并实现物理页分配与回收。本次实验在这个基础上加入中断与异常机制，使内核能够暂时离开当前执行位置，处理时钟事件或指令异常，再恢复寄存器并继续执行。

我们围绕“保存现场—进入处理函数—处理事件—恢复执行”展开设计。Trap 发生时，硬件记录 `sepc`、`scause` 和 `stval`，更新 `sstatus`，跳转到 `stvec` 指定的入口。汇编入口将通用寄存器和这些 CSR 保存到内核栈，形成 Trap frame。C 语言处理函数通过帧指针读取原因、处理事件并设置返回地址，最后由恢复汇编取回寄存器，执行 `sret`。

```text
OpenSBI → kern_entry：建立映射，设置内核栈
  → kern_init：清零 BSS，解析 DTB，初始化控制台和物理内存
  → idt_init：设置 sscratch 和 stvec
  → clock_init：设置第一次时钟事件，开启时钟中断源
  → intr_enable：开启 S 模式全局中断

Trap → __alltraps → SAVE_ALL
  → a0 = sp → trap(tf) → trap_dispatch(tf)
  → interrupt_handler(tf) 或 exception_handler(tf)
  → __trapret → RESTORE_ALL → sret → 继续执行
```

实现顺序也按照这条主线推进：先导入框架并恢复内存管理基线，再打通汇编入口与 C 函数之间的调用和返回，接着完成时钟与异常处理，最后用连续中断和不同长度的异常指令验证整个过程。

## 三、Trap 入口与上下文恢复

### 3.1 根据保存布局设计恢复过程

我们首先对照 `SAVE_ALL` 和 `struct trapframe` 核对现场布局。RV64 下，每个 `uintptr_t` 占 8 字节，32 个通用寄存器槽加上 4 个 CSR 槽，共占 `36 × 8 = 288` 字节。288 是 16 的整数倍，建立帧后仍保持 C 函数调用所需的栈对齐。

| 字段 | 槽号 | 字节偏移 | 用途 |
| --- | --- | --- | --- |
| x0 | 0 | 0 | 保存零值 |
| x1 / ra | 1 | 8 | 保存原返回地址 |
| x2 / sp | 2 | 16 | 保存建立 Trap frame 前的栈指针 |
| x3～x31 | 3～31 | 24～248 | 保存其余通用寄存器 |
| status / sstatus | 32 | 256 | 保存特权级与中断状态 |
| epc / sepc | 33 | 264 | 保存 Trap 返回地址 |
| badvaddr / stval | 34 | 272 | 保存异常附加信息 |
| cause / scause | 35 | 280 | 保存 Trap 原因 |

sp 的处理决定了恢复顺序。`SAVE_ALL` 先把旧 sp 写入 `sscratch`，再向下分配 288 字节，最后把旧 sp 放入第 2 槽。因此，我们以建立帧后的 sp 作为加载基址，在其余寄存器恢复完成后，再从第 2 槽取回原 sp。

### 3.2 实现 RESTORE_ALL

`RESTORE_ALL` 先用 t0、t1 读取帧内 `status` 和 `epc`，写回 `sstatus` 和 `sepc`；随后恢复 x1、x3～x31，最后恢复 x2。t0、t1 在读取 CSR 保存值时被用作临时寄存器，也会在通用寄存器恢复阶段取回原值。

`cause` 和 `badvaddr` 供 C 函数分类和诊断使用，返回时由通用寄存器、`sstatus` 和 `sepc` 共同恢复执行状态。x0 的硬件值恒为零，恢复宏从 x1 开始加载。

中断发生时，被打断的代码可能正在使用参数寄存器或临时寄存器。因此，我们按完整现场恢复 a、t、s、ra、gp、tp 和 sp，使处理函数使用寄存器之后，原代码仍能继续使用之前的计算结果。

### 3.3 建立汇编与 C 函数的调用关系

`SAVE_ALL` 执行后，sp 指向帧首。我们通过 `mv a0, sp` 将帧地址作为第一个参数传入，再用 `jal trap` 调用 C 函数。原 a0 和 ra 已保存在帧内，恢复阶段会将它们取回。

C 函数返回后撤销自己的栈空间，sp 重新指向 Trap frame，控制流进入 `__trapret`。此时恢复宏读取的是处理后的帧内容，异常函数对 `tf->epc` 的修改也就成为新的 `sepc`，决定 `sret` 后的执行位置。

### 3.4 观察 sret 返回状态

本实验的内核和触发样例运行在 S 模式。Trap 入口处保存的 `sstatus.SPP=1`，执行 `sret` 后返回 S 模式，同时完成 `SIE=SPIE`、`SPIE=1`、`SPP=0` 的状态更新。

调试时，四次异常和三次时钟返回后的 `$priv` 都为 1。异常样例在开启全局中断之前执行，返回后的 SIE 为 0；时钟中断在全局中断开启后发生，返回后的 SIE 为 1。我们将这些结果与帧中的状态位逐项对应，检查恢复过程。

## 四、中断处理与时钟链路

### 4.1 中断分类

`trap_dispatch()` 根据 `scause` 最高位区分中断和异常。中断处理函数清除最高位，使用剩余编号选择分支。例如，实际时钟中断的 cause 为 `0x8000000000000005`，对应 `IRQ_S_TIMER=5`。

对框架中定义的软件中断、定时器中断和外部中断，函数输出相应类型提示；对未知编号，先输出 `Unknown interrupt: cause N`，再打印完整 Trap frame。测试中构造不同 cause，逐项检查提示、计数器和现场内容。

### 4.2 连续时钟与关机设计

`clock_init()` 开启 `sie` 中的时钟中断使能位，设置第一次事件并将 `ticks` 清零；`intr_enable()` 再开启 `sstatus.SIE`。定时器到期后，处理函数按以下顺序执行：

```c
clock_set_next_event();
++ticks;
if (ticks % TICK_NUM == 0) {
    print_ticks();
    if (ticks / TICK_NUM >= SHUTDOWN_AFTER) {
        sbi_shutdown();
    }
}
```

OpenSBI 每次设置一个截止时间，因此我们在每次处理中安排下一事件，使时钟持续触发。`timebase=100000`，QEMU 的 time 频率为 10 MHz，对应约 10 ms 的事件间隔。

我们取 `TICK_NUM=100`，每处理 100 次时钟中断输出一行 `100 ticks`；取 `SHUTDOWN_AFTER=10`，在第十次输出后关机。使用 `ticks / TICK_NUM` 计算输出次数，使计数、输出和关机共享同一状态。

| 进入时 ticks | 处理后 ticks | 观察到的行为 |
| ---: | ---: | --- |
| 0 | 1 | 设置下一事件，继续运行 |
| 98 | 99 | 继续计数 |
| 99 | 100 | 输出第 1 行 `100 ticks` |
| 100 | 101 | 进入下一统计周期 |
| 998 | 999 | 继续计数 |
| 999 | 1000 | 输出第 10 行，调用 SBI 关机 |

时钟中断返回时保留原 epc，继续被打断的执行流。我们在这些边界观察整个 288 字节帧，处理前后内容保持一致；最后一次中断到达 `sbi_shutdown()`。

### 4.3 中断屏蔽与临界区

我们结合页分配器阅读了中断保护过程。`__intr_save()` 读取 SIE，保存原使能状态并关闭中断；`__intr_restore(flag)` 根据保存值恢复。每层临界区使用自己的状态变量：外层进入时保存开启状态，内层进入时保存关闭状态，最终由外层退出恢复开启。

`local_intr_save(x)` 使用 `do { ... } while (0)` 将宏体组织为一条语句，使其能够按普通语句的形式放入条件分支。页分配接口用这组操作包围空闲链表修改，保持单核执行中的数据结构更新完整。

## 五、异常处理与执行恢复

### 5.1 根据指令编码更新返回地址

异常由当前指令触发，`sepc` 保存触发指令的地址。我们对非法指令和断点采用跳过指令、继续执行的处理方式：先输出原 epc，再根据指令长度更新帧内返回地址。

| 异常 | 输出 | 返回地址处理 |
| --- | --- | --- |
| `CAUSE_ILLEGAL_INSTRUCTION` | `Illegal instruction at` 和原地址 | 跳过触发指令 |
| `CAUSE_BREAKPOINT` | `Breakpoint at` 和原地址 | 跳过触发指令 |
| 其他异常 | 完整 Trap frame | 保留现场，输出诊断信息 |

本实验使用的 RV64IMAC 支持 16 位压缩指令和 32 位指令。我们从 epc 读取首个 16 位半字，最低两位不为 `11` 时前进 2 字节，否则对本实验的 32 位触发指令前进 4 字节：

```c
unsigned short insn = *(const unsigned short *)tf->epc;
tf->epc += (insn & 3) == 3 ? 4 : 2;
```

使用半字读取也能处理两字节对齐的触发点。更新后的 `tf->epc` 由恢复宏写入 `sepc`，`sret` 随后跳到下一条指令。其他异常分支直接打印帧内容，保留诊断所需的原状态。

### 5.2 异常触发与恢复现象

我们设置四个汇编触发点，分别执行 16 位断点、32 位断点、16 位非法指令和 32 位非法指令。GDB 读取触发地址的实际编码，检查 cause 和 epc，并在预期返回位置设置硬件断点。

| 触发样例 | scause | 原 epc | sret 后的 PC |
| --- | --- | --- | --- |
| 16 位断点 `0x9002` | `0x3` | `0xffffffffc02000f0` | `0xffffffffc02000f2` |
| 32 位断点 `0x00100073` | `0x3` | `0xffffffffc02000f4` | `0xffffffffc02000f8` |
| 16 位非法指令 `0x0000` | `0x2` | `0xffffffffc02000fa` | `0xffffffffc02000fc` |
| 32 位非法指令 `0x0000007b` | `0x2` | `0xffffffffc02000fe` | `0xffffffffc0200102` |

四条异常提示各出现一次，输出地址与修改前的 epc 一致。每次 `sret` 后都到达表中的下一执行位置，随后运行到样例结束标记。四种编码分别得到 2、4、2、4 字节的地址增量。

函数级测试还检查了六组编码与异常原因组合，比较提示字符串和整个帧，结果均为仅 epc 改变。对十三种其他原因，我们将 epc 设为地址 1，观察到函数直接调用帧输出，现场内容保持原值。

### 6.2 实现与调试中遇到的问题

**内存边界常量缺失。** 迁移 `page_init()` 后，编译器报告 `PHYSICAL_MEMORY_END` 和 `KERNEL_BEGIN_PADDR` 未定义。我们根据 Lab3 已有的虚拟地址边界和映射偏移，分别用 `KERNTOP - PHYSICAL_MEMORY_OFFSET` 和 `KERNBASE - PHYSICAL_MEMORY_OFFSET` 定义物理地址边界，随后通过编译和物理页自检。

**汇编样例改变了镜像入口。** 加入测试文件后，QEMU 打印 OpenSBI 信息，却始终没有命中 `kern_init`。反汇编发现测试函数排在镜像起始地址，`kern_entry` 被放到了后面。我们将入口放入 `.text.kern_entry`，让链接脚本优先收集，重新启动后正常命中初始化断点。

**调试时机与返回断点选择。** GDB 在复位阶段读取高地址代码时报告内存不可访问，我们调整为先执行到 `kern_init`，再反汇编返回路径。单步执行 `sret` 时又停在下一次 Trap 入口，于是改在帧内 epc 对应的位置设置临时硬件断点，直接观察返回后的 PC、寄存器和特权级。

**不同工具链的汇编兼容。** 柯云超的旧工具链采用 `ARCH=rv64imac` 完成构建；最终集成时，新版汇编器对框架旧 CSR 名 `sbadaddr` 报错，我们增加 `-Dsbadaddr=stval`，将名称映射到同一个 CSR 0x143，随后构建通过。

**GDB 与模拟器版本选择。** 柯云超原有 GDB 缺少 Python 支持，改用 `gdb-multiarch` 12.1 运行自动检查。入口恢复测试在 QEMU 4.1.1 的返回状态位断言处停止，换用 QEMU 6.2 后，四次异常和三次时钟返回全部通过；最终集成在 QEMU 7.0 上完成相同检查。

这些问题促使我们把输入状态、寄存器布局、链接位置和工具版本写入调试步骤。遇到异常现象时，先用编译错误、反汇编和断点确定发生位置，再调整实现或验证方法。

## 八、实验总结与认识

### 8.1 实验实现与操作系统原理

| 知识点 | 本次设计与观察 |
| --- | --- |
| 现场保存与恢复 | 用内核栈上的 Trap frame 保存通用寄存器和返回状态，处理结束后取回原值；逐寄存器比较检查了这一过程 |
| 同步异常与异步中断 | 两者共用入口，通过 cause 分流；指令异常按长度更新 epc，时钟中断保留 epc |
| 特权级与返回机制 | SPP 决定返回模式，SPIE 保存中断使能状态；本次观察到 S → S 返回及 SIE 的恢复 |
| 调用约定 | a0 传递帧指针，sp 保持对齐，ra 和参数寄存器从帧中恢复 |
| 定时器与时间管理 | 每次处理中安排下一事件，维护 ticks，并在固定计数边界执行输出和关机 |
| 临界区保护 | 页分配操作保存并关闭本核中断，修改空闲链表后恢复原使能状态 |

Trap 现场恢复与进程切换都涉及寄存器状态，但本实验沿原内核执行流返回，进程切换还需要选择运行对象并切换其栈与地址空间。周期中断提供了进入内核的时机，调度器则进一步利用这一时机进行时间片分配。实验中的临界区保护依靠本核中断屏蔽，多核共享数据的互斥还需要锁与内存顺序机制。

后续值得继续研究的内容包括用户态与内核态的栈切换、系统调用、缺页恢复、进程调度和多核同步。它们分别扩展了本次实验中的入口、分发、恢复和并发控制机制。

### 8.2 AI 协作与调试收获

我们在使用 AI 生成代码时，先把已有接口、状态变化和检查方法写清楚。恢复宏的关键要求是“按实际帧布局恢复，原 sp 最后恢复”；时钟函数的关键要求是“重设事件、计数、输出、关机保持顺序”；异常函数的关键要求是“根据指令编码更新 epc，并到返回目标检查执行位置”。这些要求将实现与验收联系起来，也让生成结果更容易逐项检查。

调试过程中，反汇编帮助我们找到镜像入口和触发指令，GDB 帮助我们把帧内容与处理器状态对应起来。尤其是异常恢复，帧内 epc 的变化、恢复后的 sepc 和 `sret` 后的 PC 构成了一条完整的观察链。通过这条链，我们把“修改返回地址”落实到了实际控制流，也形成了从设计状态到运行现象的验证方法。
