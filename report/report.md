## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本实验回答的是：一个不依赖宿主操作系统运行库的最小 RISC-V 内核，如何被放入模拟机器的内存、取得控制权，并输出第一条信息。

可以分为构建链和执行链。构建链为 C/汇编源码经交叉编译得到目标文件，由链接脚本确定地址并生成 `bin/kernel`，再由 `objcopy` 转为 `bin/ucore.img`。执行链为 QEMU 复位代码转入 OpenSBI，OpenSBI 完成固件初始化并移交控制权，内核设置自己的栈后进入 `kern_init`，最终经 SBI 打印信息。

### 3.2 功能的逐步衔接

1. **先确定内存布局和入口。** `tools/kernel.ld` 设置基址 `0x80200000` 和入口符号 `kern_entry`，否则加载镜像的地址和链接时假设的地址可能不一致。
2. **再构建内核镜像。** Makefile 编译、链接并产生二进制镜像，同时保留带调试符号的 ELF 文件供 GDB 使用。
3. **由模拟器装载、固件移交控制权。** 本工程的 `-device loader,file=bin/ucore.img,addr=0x80200000` 在 CPU 执行前将镜像放入内存；复位代码和 OpenSBI 负责后续执行流。
4. **建立 C 代码运行的基础。** `kern_entry` 设置 `sp`，随后尾调用 `kern_init`。`kern_init` 清零 `[edata, end)`，打印启动信息并进入无限循环。
5. **最后用调试器核对每一步。** 在复位位置、固件入口和内核入口观察 PC，并单步核对栈指针和尾调用行为。

## 四、实验内容与实现

### 功能模块：编译、链接与镜像装载

**负责人：** 待小组确认。

涉及 `Makefile`、`tools/function.mk` 和 `tools/kernel.ld`。本模块属于构建配置，没有新增 C 函数接口。

链接脚本的 `OUTPUT_ARCH(riscv)` 指定架构，`ENTRY(kern_entry)` 指定 ELF 入口，`BASE_ADDRESS = 0x80200000` 确定段布局起点。`.text` 存放指令，`.rodata` 存放只读数据，`.data`/`.sdata` 存放已初始化数据，`.bss`/`.sbss` 对应需要运行时清零的对象。

本次 `readelf` 实测 ELF 入口为 `0x80200000`。`bin/kernel` 含符号和调试信息，GDB 使用它识别源码位置；`bin/ucore.img` 是去除 ELF 容器信息后的裸镜像，由 QEMU 按指定地址装载。`ENTRY` 本身不保证裸镜像起始字节就是入口指令，因此还需要核对实际符号地址和反汇编。本次 `kern_entry` 确实位于镜像基址。

### 功能模块：入口和 C 初始化

**负责人：** 待小组确认。

涉及汇编符号 `kern_entry`、`bootstack`、`bootstacktop`，以及：

```c
int kern_init(void) __attribute__((noreturn));
void *memset(void *s, char c, size_t n);
```

`entry.S` 在 `.data` 中以页为单位对齐启动栈。`KSTACKPAGE = 2`、`PGSIZE = 4096`，因此栈空间为 8192 字节。本次 `bootstack = 0x80201000`，`bootstacktop = 0x80203000`，栈向低地址增长。

`kern_init` 使用 `memset(edata, 0, end - edata)` 满足 C 中静态存储对象默认零初始化的要求，随后调用 `cprintf` 输出消息，最后在无限循环中停留。它被声明为不返回，因此入口不需要建立一个期待返回的调用链。

本次最小镜像中 `edata = end = 0x80203008`，BSS 长度为零。我们验证了清零调用存在及其参数范围，但没有据此声称验证了非空 BSS 区域的清零效果。

### 功能模块：通过 SBI 输出

**负责人：** 待小组确认。

主要已有接口如下：

```c
int cprintf(const char *fmt, ...);
int vcprintf(const char *fmt, va_list ap);
void cons_putc(int c);
void sbi_console_putchar(unsigned char ch);
uint64_t sbi_call(uint64_t sbi_type, uint64_t arg0,
                  uint64_t arg1, uint64_t arg2);
```

输出链为 `cprintf -> vcprintf -> vprintfmt -> cputch -> cons_putc -> sbi_console_putchar`。`vprintfmt` 负责格式化，`cputch` 输出一个字符并更新字符计数，`cons_putc` 将字符交给 SBI 服务。

当前代码使用旧版 SBI 接口：字符输出服务号为 1，参数通过 `a0` 等寄存器传递，服务号置于 `a7`，`ecall` 将请求交给固件处理。这与现代扩展式 SBI 接口的调用约定不同，不能混用服务号。

### 练习1：理解内核启动中的程序入口操作

**负责人：** 待小组确认。

**`la sp, bootstacktop` 完成什么操作，目的是什么？**

它将 `bootstacktop` 的地址放入栈指针寄存器 `sp`，建立内核自己的启动栈。进入 C 函数后，保存返回地址、局部变量和调用其他函数都可能使用栈；继承 OpenSBI 的栈不能作为内核长期使用的栈。

`la` 是伪指令。本次反汇编为 `auipc sp, 0x3` 和 `mv sp, sp`，后一条对应零偏移的地址调整。执行两条机器指令后，PC 为 `0x80200008`，SP 为 `0x80203000`，与 `bootstacktop` 一致。

**`tail kern_init` 完成什么操作，目的是什么？**

它把执行流转移到 `kern_init`，采用尾调用语义，不为返回入口建立新的返回地址。当前构建经链接松弛后为一条压缩跳转指令，地址 `0x80200008` 跳向 `0x8020000a`。不能把这次反汇编推广为所有工具链下的固定展开形式。

实测跳转前后 RA 都为 `0x80000a02`，说明跳转本身没有像普通 `call` 一样改写 RA。RA 在后续 C 函数内部调用时仍可以变化。由于 `kern_init` 不返回，尾调用符合启动流程的控制流需求。

### 练习2：使用 GDB 验证启动流程

**负责人：** 待小组确认。

#### 调试方式

在 `code/` 中用 `make debug` 启动 QEMU，`-S` 使 CPU 停在执行第一条指令之前，`-s` 打开 GDB 1234 端口。另一个终端用 `make gdb` 连接。自动记录时使用相同 QEMU 目标和 `riscv64-unknown-elf-gdb --batch -x tools/boot.gdb`。

关键手工命令如下，完整记录见 [gdb.log](./logs/gdb.log)：

```gdb
info registers pc sp
x/6i $pc
hbreak *0x80000000
continue
delete breakpoints
hbreak *0x80200000
continue
info registers pc sp ra a0 a1
p/x &bootstacktop
si
si
info registers pc sp ra
```

#### 观察结果

| 观察位置 | 实际结果 | 说明 |
|----------|----------|------|
| CPU 最初暂停位置 | PC=`0x1000`，SP=`0` | QEMU `virt` 的复位 ROM 代码 |
| 复位代码跳转目标 | 地址 `0x1018` 存放 `0x80000000` | 供间接跳转读取的固件入口地址 |
| OpenSBI 入口 | PC=`0x80000000`，`a0=0`，`a1=0x1020` | 已离开复位代码，开始执行固件 |
| 内核入口 | PC=`0x80200000`，SP=`0x8001bd80` | 此时尚未执行内核栈设置 |
| 完成栈设置 | PC=`0x80200008`，SP=`0x80203000` | SP 等于 `bootstacktop` |
| 转入 C 入口 | PC=`0x8020000a`，RA=`0x80000a02` | `kern_init` 入口，尾调用未改写 RA |

#### 最初的几条指令在哪里，完成什么功能？

本次从 `0x1000` 开始执行，观察到以下五条有效指令：

| 地址 | 指令 | 作用 |
|------|------|------|
| `0x1000` | `auipc t0, 0` | 以当前 PC 建立复位代码基地址 |
| `0x1004` | `addi a1, t0, 32` | 将 `0x1020` 放入 `a1`，作为传给固件的设备树位置 |
| `0x1008` | `csrr a0, mhartid` | 读取硬件线程编号，作为固件参数 |
| `0x100c` | `ld t0, 24(t0)` | 从 `0x1018` 读取固件入口 `0x80000000` |
| `0x1010` | `jr t0` | 间接跳转进入 OpenSBI |

`0x1000` 处是 QEMU 设置的复位跳板，不是我们内核的入口，也不能直接等同于位于 `0x80000000` 的 OpenSBI 主体。随后 OpenSBI 在机器模式完成初始化，再将执行流交给运行于监督模式的内核。

本次没有给 OpenSBI 逐条执行所有初始化指令，而是在固件和内核入口设置硬件断点，验证阶段之间的控制流，并对复位代码和内核入口逐条观察。

#### 对装载时机的核对

CPU 仍停在 `0x1000` 时，`x/4i 0x80200000` 已能读到 `kern_entry` 的指令。这表明本工程的 QEMU loader 在 CPU 运行之前已将镜像装入该地址。OpenSBI 随后负责初始化和移交执行权。指导书中的 `watch *0x80200000` 提示在这种装载方式下不一定观察到写入事件，因此本次采用入口断点验证，而不声称捕获了不存在的运行中装载写入。

### 拓展：现代笔记本的启动流程

现代 PC 通常由 UEFI 固件初始化硬件并选择启动项，再执行 GRUB 或 Windows Boot Manager 等引导程序，最终加载操作系统内核。本实验与之共同体现了固件初始化、确定入口和移交控制权的分层过程，但 RISC-V 的 OpenSBI 服务、特权级约定与 PC 的具体固件接口不同。

## 六、实验总结与收获

### 对操作系统的理解

| 实验知识点 | 对应 OS 原理 | 联系与差异 |
|------------|-------------|------------|
| 复位代码、固件和内核入口 | 启动与特权级 | 启动经历分层控制权交接；本实验仅展示最小初始化，没有完整设备发现和多核启动 |
| 链接脚本与段布局 | 内存组织 | 构建时确定静态对象地址；本实验尚未建立页表和动态内存分配机制 |
| 启动栈与 C 调用 | 执行上下文 | 栈支持保存状态和函数调用；这里仅有一条内核执行流，没有进程栈切换 |
| BSS 清零 | 程序装载与运行环境 | 静态零初始化需要运行环境保证；当前镜像的 BSS 恰好为空 |
| SBI `ecall` 输出 | 特权服务与陷入 | 体现监督模式向机器模式固件请求服务；与用户态向内核发起系统调用的服务层级不同 |
| QEMU/GDB 调试 | 机器状态观察 | 可检查 PC、寄存器和内存；模拟环境的复位地址与真实硬件平台可能不同 |

本实验尚未对应的 OS 重要内容包括进程与线程管理、调度、分页与虚拟内存、物理内存分配、设备中断处理、文件系统、同步互斥以及用户态系统调用。这些功能不能从一条启动消息推断为已实现。

### AI 协作开发的经验

本次处理过程支持以下工程结论：

1. 先核对真实源码和 Makefile，再决定需要实现什么，能够避免为不存在的填空任务增加代码。
2. 指导书中的描述应与实际装载命令和调试结果相互核对；本次通过复位前检查内存识别了 loader 的装载时机。
3. 验证结论必须限定范围。本实验验证的是编译、启动和入口调试，不能把这些结果推广为已完成进程、内存或文件系统功能。
4. 原始日志、符号信息和可重复执行的命令，比单独一张结果截图更便于复核。

上述内容是本次过程的技术总结。每位成员的个人理解、实际 AI 使用经验与个人收获仍需由本人复核、补充，不能将 AI 整理的材料直接当作个人经历。
