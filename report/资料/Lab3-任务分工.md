## 2. A：Trap 入口与上下文恢复

### 实现范围

- 在新的 Lab3 框架中，按练习要求补齐带 `lab2` 注释的必填位置，复用此前的设计约束和提示词。先交付能构建的共同基线；只迁移框架需要的部分，避免把 Lab2 的所有扩展整体搬入。
- 阅读提供的 `SAVE_ALL`、`struct pushregs` 和 `struct trapframe`，列出保存位置与恢复位置的对应关系。
- 实现 `RESTORE_ALL`，正确恢复通用寄存器、`sstatus`、`sepc` 和原来的 `sp`；明确哪些字段用于恢复，哪些用于诊断。
- 完成 `__alltraps`：将当前 Trap frame 按调用约定传给 `trap(struct trapframe *tf)`，返回后衔接 `__trapret` 和 `sret`。
- 保持 `SAVE_ALL`、结构体布局和 `trap()` 签名不变。恢复顺序不能过早破坏访问 Trap frame 所依赖的 `sp`。

### 验证与验收

- [ ] Lab2 必填项补齐，Lab3 基线能够构建。
- [ ] 对照汇编与结构体核对帧大小、字段偏移及栈对齐。
- [ ] 在 `__alltraps`、`trap()`、`__trapret` 设置断点，记录同一次 Trap 的栈指针、帧地址、返回地址与关键 CSR。
- [ ] 验证传入 `trap()` 的指针确实指向已保存的现场；验证通用寄存器与原 `sp` 恢复正确。
- [ ] 与 B/C 集成后，验证时钟中断和异常都能经过同一返回路径；C 修改的 `tf->epc` 能成为实际返回地址。

独立准备阶段可先做反汇编、帧布局检查，并在单独验证版本中使用最小处理桩检查入口/返回；这些检查之后仍需真实 Trap 验证。

### 报告范围

负责整体执行主线、环境与 Lab2 衔接说明、保存/恢复布局、调用约定、`sret` 返回机制，以及 A 部分 spec、prompt、实际问题和证据。解释本实验实际的返回特权级，不把所有 `sret` 都描述成固定返回 U 模式。

## 3. B：中断处理与时钟链路

### 实现范围

- 只修改 `interrupt_handler(struct trapframe *tf)` 的指定待填区域。
- 根据 `tf->cause` 区分框架列出的中断类型；已列类型输出相应提示，未知类型调用已有的 `print_trapframe(tf)`。
- 对 `IRQ_S_TIMER`：设置下一次时钟事件、每次中断递增一次 `ticks`、在 `TICK_NUM` 的整数倍输出规定信息，累计输出达到 `SHUTDOWN_AFTER` 时调用框架关机接口。
- 核对 `clock.c`、`intr.c`、`sbi.h` 及常量的实际定义，输出格式、阈值和关机函数均以本次 Lab3 框架为准。
- 阅读 `sync.h` 及内存分配中的关中断保护，解释中断状态保存/恢复及 `do { ... } while (0)` 的作用；这属于理解和报告任务。

### 验证与验收

- [ ] 连续多次时钟中断都能到达，排除只设置第一次事件的问题。
- [ ] 核对 `TICK_NUM - 1`、`TICK_NUM`、`TICK_NUM + 1` 附近的计数和输出行为。
- [ ] 核对关机阈值前后：打印次数正确、没有提前关机或少打印一次。
- [ ] 已列非时钟中断分支和未知中断兜底符合要求；时钟处理中不人为跳过被打断的指令。
- [ ] 三部分合并后完成构建、`make qemu` 和框架提供的 `make grade`，保存真实日志与截图；额外核对评分脚本未覆盖的验收项。

独立准备阶段可用单独测试入口构造 Trap frame，并替代定时器、打印和关机接口检查分支与计数；此时只证明处理函数逻辑，持续硬件中断和真实关机需在 QEMU 中验证。

### 报告范围

负责中断识别、时钟事件重设、计数与关机、中断使能和临界区保护、最终测试章节，以及 B 部分 spec、prompt、实际问题和证据。

## 4. C：异常处理与指令恢复

### 实现范围

- 只修改 `exception_handler(struct trapframe *tf)` 的指定待填区域。
- 处理 `CAUSE_ILLEGAL_INSTRUCTION` 和 `CAUSE_BREAKPOINT`，按框架规定格式输出信息。
- 根据实际异常指令及编码判断长度，正确更新 `tf->epc`；覆盖本框架涉及的 16 位/32 位指令场景，不能对所有异常统一写死 `+4` 或 `+2`。
- 未要求具体恢复的异常调用已有的 `print_trapframe(tf)`，不额外实现缺页处理或系统调用。
- 准备独立的异常触发样例和验证说明，触发代码放在验证入口或单独补丁中；正式提交版本按框架允许的范围保留。

### 验证与验收

- [ ] 非法指令异常能够识别，规定信息输出正确。
- [ ] 断点异常能够识别，规定信息输出正确。
- [ ] 用反汇编确认触发指令的实际编码与长度，记录异常前的 `epc` 和处理后的返回位置。
- [ ] 执行异常之后的标记语句，证明控制流确实向后继续，无重复陷入同一异常的循环。
- [ ] 需要覆盖的不同指令长度分别验证；其他异常的兜底输出另作验证，不将它误判为成功恢复执行。
- [ ] 合并 A/B 的正文和证据链接，核对报告模板、图片路径和所有要求是否有对应内容。

独立准备阶段可先完成编码分析、反汇编和构造 Trap frame 的函数验证；实际触发与 `sret` 返回仍需集成 A 的入口/恢复实现。

### 报告范围

负责异常分类、非法指令/断点、指令长度与 `epc`、异常恢复验证，以及 C 部分 spec、prompt、实际问题和证据。负责最终报告的基本信息、分工表、目录链接和总结汇总，各人的知识点与 AI 使用经历由本人提供。

B/C 虽然修改同一个 `trap.c`，但分别拥有不同函数，不互相格式化或重排整份文件。测试桩和验证补丁不混入正式函数补丁。

### 开展顺序

1. **共同起点**：取得同一版 Lab3 原始框架，核对实际常量、输出要求、待填位置和评分脚本。当前内层 `labs/` 已切换到本地 `lab3` 分支，但仍继承 Lab2 内容；A 先导入教师 Lab3 原始框架，三人基于同一版本开展实现。
2. **并行准备**：A 整理 Lab2 衔接和汇编布局；B 准备中断处理及计数边界验证；C 准备异常处理和触发指令。B/C 的实现和函数级验证可以先进行。
3. **短暂共享基线**：A 提交 Lab2 必填项基线及入口/恢复补丁，B/C 引入后各自完成 QEMU 实际验证。A 的基础补丁应优先交付，无需等 A 的报告写完。
4. **合并收尾**：B 合并三份代码补丁并运行整体回归；A 核对集成后的现场与返回，C 核对异常后继续执行，并组装最终报告。
5. **交叉检查**：A 检查 C 的返回地址，B 检查 A 的重复中断返回，C 检查 B 的最终输出与报告证据。三人均亲自运行一次完整流程。

三部分共享真实 Trap 入口，因此端到端运行存在必要依赖；通过固定接口、独立文件/函数和先做函数级验证，可将等待集中在最后的集成阶段。
