# Lab3 运行与 A 的调试

我在 WSL2 Ubuntu 24.04.4 中使用 RISC-V GCC 13.2.0、QEMU 8.2.2 和 gdb-multiarch 15.1 完成本次验证。版本记录见 [environment.json](../evidence/A-20261104/environment.json)。

## 构建与启动

在仓库根目录进入 WSL，再执行：

```bash
cd code
make
make qemu
```

我使用 Makefile 默认的 `rv64imac_zicsr_zifencei` 和 `lp64`。当前基线会打印 Best-Fit 自检成功和时钟初始化信息，B 的处理函数接入后继续完成时钟重设、输出和关机。退出 QEMU 时按 Ctrl+A，松开后按 X。

## A 的自动验证

```bash
make check-a
```

我在临时目录复制源码，加入四个异常触发点、两个最小处理桩和计数结束标记，再由 GDB 逐次检查实际 Trap。结果目录默认为 `report/evidence/A-20261104/`，也可以指定另一个输出目录：

```bash
python3 tools/check_a.py --output ../report/evidence/A-recheck
```

通过时输出：


我主要查看 `trap-gdb.log` 和 `trap-summary.json`。`fixture-disassembly.log` 给出触发点编码，`fixture-qemu.log` 记录从启动到计数完成、执行后续标记的串口输出。`tested-source.json` 保存所测 `trapentry.S` 的 SHA-256。

## 手动观察共同入口

终端一：

```bash
make debug
```

终端二：

```bash
make gdb
```

我在 GDB 中使用以下断点和检查命令：

```gdb
hbreak *kern_init
continue
delete breakpoints
hbreak *__alltraps
hbreak *trap
hbreak *__trapret
continue
info registers sp ra a0 sstatus sepc scause stval
continue
p/x $a0
p/x $sp
p *(struct trapframe *)$a0
p sizeof(struct trapframe)
continue
info registers sp
x/36gx $sp
disassemble __trapret
```

入口断点位于 `SAVE_ALL` 前，我在这里记录原 sp。`trap` 第一条指令处的 a0 和 sp 应相等，并比原 sp 小 288；`__trapret` 处 sp 应再次等于帧地址。恢复末尾应从第 2 槽取回原 sp，随后执行 `sret`。我在帧内 `epc` 指向的位置另设临时硬件断点，核对最终 PC 和 `$priv`。

## B/C 接入位置

我们在 `kern/trap/trap.c` 的 `lab3 function2` 区域继续实现两个处理函数。B 填写 `interrupt_handler()`，C 填写 `exception_handler()`，共同使用 `trapframe` 和已有分发接口。当前框架定义 `TICK_NUM=100`，提供 `clock_set_next_event()`、`ticks` 和 `sbi_shutdown()`；关机次数常量 `SHUTDOWN_AFTER` 需要在处理区域中补充。

合并后，我们运行 `make`、`make qemu` 和 `make grade`。评分脚本包含上下文恢复与断点返回、非法指令返回、连续时钟中断三组检查。A 的独立验证入口继续用于定位保存与恢复路径，正式处理函数的输出、计数边界和关机行为由整体验证检查。
