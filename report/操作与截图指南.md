# Lab1 操作与截图指南

这份指南用于成员亲自运行实验、检查输出并补充报告图片。Lab1 的主题是最小内核与启动流程；环境配置是前置准备，本次不执行 `make grade`。

命令分为 Windows PowerShell、Ubuntu Bash 和 GDB 三种环境。不要将 GDB 命令输入 Bash，也不要在 PowerShell 中直接执行 `make`。

## 0. 打开 Ubuntu，进入代码目录

在 Windows Terminal 的 PowerShell 标签页输入：

```powershell
wsl -d Ubuntu-22.04
```

进入 Ubuntu 后执行：

```bash
cd /home/kyc/project/os/NKUOS/code
pwd
```

应看到 `/home/kyc/project/os/NKUOS/code`。以下所有 Bash 命令都在该目录运行。

如果 GCC、GDB 或 QEMU 提示找不到命令，先执行本机已有的环境配置：

```bash
source /home/kyc/.local/opt/riscv/env.sh
```

图片目录的 Windows 路径是：

```text
\\wsl.localhost\Ubuntu-22.04\home\kyc\project\os\NKUOS\report\images
```

可以在资源管理器地址栏打开它。每完成下面一个步骤，用 `Win+Shift+S` 截取对应终端，保存为指定 PNG 文件。截图中保留命令和关键结果；内容太长时可缩小终端字号或分为两张，不要裁掉关键输出。

## 4. 启动新的暂停调试实例

需要两个 Ubuntu 终端。

终端一，在 `code/` 中运行：

```bash

```

CPU 此时由 `-S` 暂停。终端一没有启动输出属于正常现象，保留它运行。

另开 Windows Terminal 标签页，按步骤 0 进入 Ubuntu。终端二执行：

```bash

```

看到 `(gdb)` 提示符后，下面的命令全部输入终端二。

如果提示 1234 端口已占用，先退出自己此前启动的 QEMU 调试实例，再重新 `make debug`；不要随意结束其他人的进程。

## 5. 查看复位代码

```gdb
set pagination off
info registers pc sp
x/6i $pc
x/2gx 0x1018
x/4i 0x80200000
```

本机预验证应看到 PC=`0x1000`。最初的有效指令是 `auipc`、`addi`、`csrr`、`ld` 和 `jr`；`0x1018` 处存有固件入口地址 `0x80000000`。

最后一条命令在 CPU 尚未执行时查看内核地址。已经能读到内核指令，说明本工程的 QEMU loader 在 CPU 运行之前完成了镜像装载。

**截图文件：`04-reset.png`。** 保留 PC、复位指令、跳转地址和内核内存中的指令。

如果第一次连接时 PC 已经不是 `0x1000`，说明这不是新的复位调试实例。按步骤 10 退出，然后重新步骤 4，不能把后面的 PC 当作复位地址。

## 6. 到达 OpenSBI 入口

```gdb
hbreak *0x80000000
continue
info registers pc a0 a1
x/8i $pc
```

应命中断点，PC=`0x80000000`。这里开始执行 OpenSBI 主体；复位位置 `0x1000` 是 QEMU 的复位跳板。

**截图文件：`05-opensbi.png`。** 保留断点、PC、参数寄存器和指令。

## 7. 到达内核第一条指令

```gdb
delete breakpoints
hbreak *0x80200000
continue
info registers pc sp ra a0 a1
x/6i $pc
p/x &bootstack
p/x &bootstacktop
```

应停在 `kern_entry`，PC=`0x80200000`。此时尚未执行设置内核栈的指令，SP 仍来自固件。预验证栈区间为 `0x80201000` 至 `0x80203000`，以自己的输出为准。

**截图文件：`06-kernel-entry.png`。** 保留内核入口、SP/RA、入口指令和栈符号地址。

## 8. 单步验证栈设置

```gdb
set $entry_ra = $ra
delete breakpoints
si
si
info registers pc sp ra
p/x &bootstacktop
p $sp == (unsigned long)&bootstacktop
```

在本机工具链下，`la sp, bootstacktop` 展开为两条机器指令，所以单步两次。预期比较结果为 1，SP 等于栈顶，PC 到达 `0x80200008`。如果换了工具链，先检查入口反汇编，按实际展开的机器指令数单步到 `tail` 前，不要机械地固定两次。

SP 后面可能显示 `<SBI_CONSOLE_PUTCHAR>`：这是同一个地址对应的另一个符号名，不表示栈设置错误。`bootstacktop` 是预留栈区域的末端，栈实际向低地址增长。

**截图文件：`07-stack.png`。** 保留单步结果、SP、栈顶地址和比较结果。

## 9. 验证尾调用和 C 入口

```gdb
tbreak *kern_init
continue
info registers pc sp ra
p $ra == $entry_ra
p/x &edata
p/x &end
p (unsigned long)&end - (unsigned long)&edata
```

应到达 `kern_init`。RA 比较结果为 1，说明 `tail` 跳转本身没有创建新的返回地址。预验证的 PC 是 `0x8020000a`，BSS 长度是 0；以本次实际输出为准。

这里停在 C 初始化的入口，不代表 `memset` 已经执行完；BSS 长度为零时，也不能据此声称测到了非空区域清零。

**截图文件：`08-kern-init.png`。** 保留 C 入口、RA 比较结果、`edata`/`end` 和区间长度。

## 验收时要能解释的内容

1. 为什么复位地址、固件入口和内核入口分别是三个不同位置。
2. 链接脚本如何决定地址，ELF 文件和裸二进制镜像有什么区别。
3. 为什么进入 C 函数前要设置内核栈，`la` 和 `tail` 在本机怎样展开。
4. 为什么 `kern_init` 清零 BSS、如何通过 SBI 打印，以及为什么打印后进入无限循环。
5. 为什么当前 QEMU loader 方式下，内核指令在复位时已可读到。
